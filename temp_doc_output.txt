1. Objectives
Extend your Lab 2 project (same GitHub repository, same Vercel project).
Replace the demo-only Login/Register logic with real authentication backed by Supabase Auth.

Important change from Lab 2: “Login successful (demo)” / “Registration successful (demo)” messages are replaced by a real Supabase account. 2. Requirements
2.1 Create a Supabase project
Create a free project at supabase.com. In Project Settings → API, copy the Project URL and the anon / public key (never the service_role / secret key — do not put it in your code or your submission).
Leave email/password sign-up enabled (it is on by default under Authentication → Providers → Email).
Turn off “Confirm email” in Authentication → Providers → Email (uncheck it and save). With it off, a new account is usable immediately after sign-up instead of waiting for a confirmation email — this is what lets both you and the grader actually log in and test the app.
Create one throwaway test account in that project (sign up through your own deployed site, or add a user in Authentication → Users). Use a dedicated password for it, not one you reuse elsewhere — it will be shared in your submission.
2.2 Supabase client
Install @supabase/supabase-js. Create a single client in its own file, e.g. lib/supabaseClient.ts, built from environment variables NEXT_PUBLIC_SUPABASE_URL and NEXT_PUBLIC_SUPABASE_ANON_KEY. Do not hardcode the keys inline in a component.
2.3 AuthContext (`useContext`)
Create contexts/AuthContext.tsx (or context/) that: keeps user, session and loading in state; loads the current session once on mount with supabase.auth.getSession(); keeps them in sync with supabase.auth.onAuthStateChange(...); and exposes signUp(email, password), signIn(email, password) and signOut().
Wrap the whole app with <AuthProvider> in the root layout (app/layout.tsx) so any page or component can read the auth state.
Use useContext(AuthContext) (directly, or through your own useAuth() hook that calls useContext internally) in at least two different components — for example the header and the account page. Do not pass the user down through props from page to page — that defeats the point of Context.
2.4 Register page (`/register`)
Keep the Lab 2 client-side validation (required fields, password ≥ 6 characters, confirm-password match) and its exact testids/messages.
On a valid submit, call signUp(email, password) from AuthContext (which calls supabase.auth.signUp), not a fake demo success. Show Supabase's own message when it fails (for example “User already registered”) in an element data-testid="error-auth". On success (with “Confirm email” off, the account is active immediately), show a message in data-testid="form-success", e.g. Registration successful.
2.5 Login page (`/login`)
Keep the Lab 2 client-side validation (required fields, valid email format) and its exact testids/messages.
On a valid submit, call signIn(email, password) from AuthContext (which calls supabase.auth.signInWithPassword). If Supabase rejects the credentials, show its message (for example “Invalid login credentials”) in data-testid="error-auth". On success, redirect to /.
2.6 Header / navigation — auth-aware
Logged out: unchanged from Lab 2 — show btn-login and btn-register.
Logged in: hide those two and instead show the user's email in data-testid="user-email" and a data-testid="btn-logout" button that calls signOut() and returns the header to its logged-out state.
2.7 A protected page (`/account`)
Create route /account. While loading is true, render nothing/a spinner. Once loading is done: if there is no user, redirect to /login (router.replace("/login")); if there is a user, render a container data-testid="account-page" showing the user's email in data-testid="account-email".
2.8 Carried over from Lab 2 (still graded)
The Home page (/) still shows the product grid (product-list, product-card, etc.) exactly as in Lab 2.
Tailwind CSS and at least two ShadCN UI components are still used. The layout is still responsive (1 column on mobile, 3+ columns on desktop).

Grading rules
Item 2 is checked against your live Supabase project using its own public sign-in API — the same request your login form sends — with the test account you submit. No dashboard access is used and nothing is created or changed beyond one throwaway test sign-up.
Items 3–8 depend on client-side JavaScript (Context, redirects, form submission) that a static page fetch cannot run. They are graded from your source code and from the rendered HTML of your Vercel site. Make sure the logic is genuinely implemented, not just described in comments.
If the test account's password is wrong, the project has “Confirm email” still on, or the account doesn't exist, item 2's live checks score 0 for the parts that depend on it — the rest of the lab is still graded normally.
Submissions may be compared for code similarity. Copied work receives 0.
